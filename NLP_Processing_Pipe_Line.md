# NLP Preprocessing Pipeline

**C++ libraries for high-performance corpus parsing, vocabulary construction, frequency-based truncation, and skip-gram context pair generation.**

This workspace contains a modular set of header-oriented C++ libraries that together implement a complete offline preprocessing pipeline for word embedding / language model training (particularly skip-gram style objectives).

The pipeline turns a raw text corpus into:
1. A compact in-memory vocabulary (hash table + dense word-ID index)
2. Optional frequency-sorted truncation to the most frequent words
3. Flat per-line token tables
4. Skip-gram context pairs (target + left/right windows)

All heavy lifting is performed in a small number of linear passes over the data. The design prioritises cache-friendly layouts, integer keys, and minimal string handling after the initial parse.

---

## Repositories & Responsibilities

| Repository | Role |
|------------|------|
| **[Hash](https://github.com/KHAAdotPK/Hash)** | Fast string → integer key generation (djb2-style) + prime utilities for open-addressing tables |
| **[Imprint](https://github.com/KHAAdotPK/Imprint)** | Optional English text cleaner (punctuation / noise removal). Hooks into Parser via macros |
| **[Parser](https://github.com/KHAAdotPK/Parser)** | Streaming corpus reader, vocabulary hash-table builder, index-table construction, frequency sorting, flat line-table materialisation |
| **[Corpus](https://github.com/KHAAdotPK/Corpus)** | Lightweight query façade over the finished vocabulary (frequency, probability, validity checks) |
| **[Pairs](https://github.com/KHAAdotPK/Pairs)** | Skip-gram context-pair generator (target + fixed-size left/right windows) |

## High-Level Pipeline

```
Raw corpus file
      │
      ▼
┌─────────────────────────────────────────────────────────────┐
│  Parser                                                     │
│  • Stream lines (optional Imprint cleaning)                 │
│  • Tokenise                                                 │
│  • Build open-addressing hash table (WordRecord_new)        │
│  • Assign dense word_ids                                    │
│  • Produce index_table[word_id] → hash_key                  │
│  • (Optional) Sort index_table by descending frequency      │
│  • Materialise flat WORDS** line tables (arrays of keys)    │
└─────────────────────────────────────────────────────────────┘
      │
      ▼
┌─────────────────────────────────────────────────────────────┐
│  Pairs                                                      │
│  • Walk each line’s token array                             │
│  • For every centre token emit a ContextPair                │
│    (left-window IDs, target ID, right-window IDs)           │
│  • Padding / unknown tokens handled with sentinel values    │
└─────────────────────────────────────────────────────────────┘
      │
      ▼
Training-ready data
(vocabulary + context pairs)
```

## Core Data Structures

### Vocabulary side (produced by Parser)

- **`WordRecord_new`**  
  One record per unique token. Holds:
  - the word string
  - frequency count (`n`)
  - dense `word_id`
  - any additional metadata

- **Hash table** (`WordRecord_new**`)  
  Open-addressing table (linear probing) indexed by the hash key generated by the Hash package.

- **`index_table`** (`size_t*`)  
  Dense mapping:  
  `index_table[word_id] = hash_key`  
  Lets any later stage go from a compact integer ID straight to the full record in the hash table.  
  Size equals the number of unique words (`bucket_used`).

### Line side

- **`WORDS`**  
  One object per corpus line:
  ```cpp
  struct WORDS {
      size_t  n;          // number of tokens on the line
      size_t* keys;       // contiguous array of hash keys
  };
  ```
  Produced by `Parser::build_lines_table()`.

### Pair side (produced by Pairs)

```cpp
struct ContextPair {
    size_t* left_context_ids;   // fixed-size window
    size_t  target_id;
    size_t* right_context_ids;  // fixed-size window
};

struct ContextPairs {
    size_t         n;
    ContextPair**  pairs;
};
```

Each line yields one `ContextPairs` object containing a pair for every token that can serve as a centre word.

## Step-by-Step Process (as exercised by the test driver)

The following matches the control flow in a typical `main` / test harness:

1. **Instantiate Parser**  
   ```cpp
   Parser parser(corpus_path);
   ```

2. **Build vocabulary**  
   ```cpp
   size_t* index_table = nullptr;
   const WordRecord_new* const* hash_table =
       parser.build_hash_table_very_new(&index_table);
   ```
   - Single pass over the file
   - Tokens are hashed, inserted (or frequency-updated) in the open-addressing table
   - Each new unique word receives the next dense `word_id`
   - `index_table` is filled with the corresponding hash keys
   - Statistics collected: total lines, total tokens, min/max tokens per line, bucket counts

3. **Optional frequency sorting / truncation**  
   ```cpp
   parser.descending_sort_index_table(
       index_table,
       parser.get_bucket_used(),
       (WordRecord_new**)hash_table);
   ```
   After this call the front of `index_table` contains the most frequent words.  
   You may then keep only the top-K entries and map the remainder to a single `<UNK>` identifier.  
   (The current test driver sorts but does not yet truncate; truncation is a trivial follow-on step.)

4. **Materialise flat line tables**  
   ```cpp
   WORDS** lines_array = parser.build_lines_table(hash_table);
   ```
   Second pass (or reuse of the already-parsed data) produces a contiguous array of hash keys for every line.  
   This representation is far more cache-friendly than the older linked-list designs.

5. **Generate skip-gram pairs**  
   ```cpp
   Pairs pairs(corpus_path);   // or any constructor that receives the needed context
   ContextPairs** contexts =
       pairs.build_pairs(parser, lines_array, (WordRecord_new**)hash_table);
   ```
   For every token that can be a centre word a `ContextPair` is emitted containing:
   - left-context word IDs (padded with a sentinel when the window falls outside the line)
   - the target word ID
   - right-context word IDs

6. **Clean-up**  
   ```cpp
   parser.free_tables_very_new(
       (WordRecord_new**)hash_table,
       lines_array,
       index_table);
   ```

At this point you possess:
- a (optionally truncated) vocabulary reachable by dense integer IDs,
- a complete set of training pairs ready for a skip-gram or similar objective.

## Optional Components

### Imprint (English cleaner)
Define the macro before including Parser headers:
```cpp
#define ITERATOR_USER_DEFINED_CLEANER_CODE
#include "Imprint/header.hh"
#include "Parser/header.hh"
```
Every line is passed through `Cleaner::cleanLine()` before tokenisation.

### Corpus (query façade)
Once the tables exist you can wrap them:
```cpp
Corpus corpus(tables);          // or the newer hash-table view
size_t  freq = corpus.frequency(word_id);
double  prob = corpus.probability(word_id);
```

### Serialisation (checkpointing)
The older code paths contain binary serialisation helpers. They are currently commented out in the test driver but remain available for large corpora that should not be re-parsed on every run.

## Build & Integration Notes

- All libraries are header-centric. Place them under a common `lib/` directory and add the appropriate `-I` paths.
- Typical include order (when using Imprint):
  ```cpp
  #define CSV_PARSER_TOKEN_DELIMITER ' '
  #define ITERATOR_GUARD_AGAINST_EMPTY_STRING
  #define ITERATOR_USER_DEFINED_CLEANER_CODE

  #include "Hash/header.hh"
  #include "Imprint/header.hh"
  #include "Parser/header.hh"
  #include "Pairs/header.hh"
  // \ldots
  ```
- The Hash package supplies both the string hasher and the prime-growth helpers used by Parser’s open-addressing table.
- Compile with a modern C++ standard (`-std=c++17` or later) and normal optimisation flags (`-O2`/`-O3`). SIMD acceleration of the hasher is a possible future enhancement but is not required for correct operation.

## Design Evolution (short history)

Earlier revisions relied on linked lists of occurrences and repeated string scans. Those designs were correct but cache-unfriendly and scaled poorly. The current path replaces them with:

- open-addressing hash tables,
- dense integer word IDs,
- contiguous per-line key arrays,
- a single index table that maps ID → hash key.

The result is a pipeline that processes multi-million-line corpora in a few minutes even on modest dual-core hardware while remaining completely under the caller’s control (no hidden global state, explicit memory ownership).
